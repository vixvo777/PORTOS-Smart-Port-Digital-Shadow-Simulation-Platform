# PORTOS — Smart Port Digital Shadow

## Recovery, Data Integration & Completion Plan

**Project:** PORTOS
**Location:** New Orleans, Louisiana, USA
**Frontend:** V3 Standalone Cesium Digital Shadow
**Historical AIS period:** 15–16 June 2019
**Goal:** Complete a working historical Digital Shadow, operational analysis and What-If simulation.

---

# 1. Project vision

PORTOS should become a historical-data-driven Smart Port Digital Shadow that allows users to:

1. Visualize actual vessel movements using AIS data.
2. Replay historical port traffic with a correct Cesium timeline.
3. Inspect individual vessels and their movement history.
4. Analyze vessel traffic, speed, anchorage activity and berth occupancy.
5. Understand historical port activity through dashboards and spatial visualizations.
6. Run What-If scenarios to test berth capacity, traffic surges and operational disruptions.
7. Compare baseline and simulated port performance.

**Important architectural decision:** We retain V3, the standalone `twin3d.html` Cesium experience. We do not revert to the V2 embedded Cesium window.

Historical observations, reference geometry and simulated vessels must remain separate.

## Issue C: Historical Cesium clock shows 2026

This is a major problem.

Selected date:

`2019-06-15`

But the current Cesium timeline shows November 2026.

The selected historical date must control:

- `viewer.clock.startTime`
- `viewer.clock.stopTime`
- `viewer.clock.currentTime`
- `viewer.clock.multiplier`
- `viewer.clock.clockRange`

Historical mode must never initialize its timeline from the computer's current date.

For the two-day dataset, support the complete June 15–16 interval.

Acceptance:

- June 16 selection displays the corresponding historical day.
- No 2026 timeline appears in historical mode.
- Playback, pause, speed and scrubbing work.

Save results in:

## 5.3 Track construction

Rules:

1. Group positions by MMSI.
2. Separate track segments.
3. Sort observations by timestamp.
4. Use recorded coordinates.
5. Preserve recorded timestamps.
6. Never connect separate segments.
7. Never interpolate across long gaps.
8. Handle stationary vessels correctly.
9. Keep source observations accessible for inspection.

## 5.4 Backend API

# 6. Phase 4 — Historical data analysis

This phase is essential. PORTOS should not be just a 3D map.

## A. Vessel traffic analysis

Calculate:

- Vessels observed per hour.
- AIS observations per hour.
- Vessel type distribution.
- Traffic density.
- Peak traffic periods.
- Spatial distribution of traffic.
- Vessel activity by port area.

Visualizations:

- Hourly traffic chart.
- Vessel type distribution.
- Traffic density heatmap.
- Spatial traffic map.

## B. Vessel movement analysis

Calculate:

- Average speed.
- Median speed.
- Maximum observed speed.
- Speed distribution.
- Slow-moving episodes.
- Stationary episodes.
- Track distance within valid observed segments.
- Direction distribution.
- Track completeness.

## C. Anchorage analysis

Identify potential anchorage activity using:

- Validated anchorage polygons.
- Vessel position.
- SOG thresholds.
- Time spent inside the zone.
- Track continuity.

If anchorage arrival and berth entry can be established, calculate waiting time.

If those events cannot be established, report anchorage dwell or low-speed episodes separately.

Do not claim observed queue waiting time without supporting event timestamps.

## D. Berth occupancy analysis

First validate the berth reference data.

Determine:

- Are berth locations official?
- Are they spatial clusters?
- Are they inferred from AIS?
- Is there a berth ID?
- Can a vessel be assigned reliably?

Then calculate, where supported:

- Occupied berths over time.
- Occupancy ratio.
- Peak simultaneous occupancy.
- Vessel distribution by berth.
- Berth utilization over the selected period.

Clearly distinguish inferred berth clusters from verified physical port capacity.

# 7. Phase 5 — What-If simulation

What-If must be independent of historical AIS playback.

Historical data provides the baseline context. Scenario results are generated by a model.

## Existing controls to preserve

- Scenario mode.
- Time horizon.
- Active berths.
- Traffic multiplier.
- Blocked berth IDs.
- Scheduling strategy.
- Run scenario.

## Scenario experiments

### Scenario 1: Baseline

Use the default operational assumptions.

### Scenario 2: Traffic surge

Increase traffic multiplier.

Observe:

- Modeled queue length.
- Modeled scheduling delay.
- Berth utilization.
- Throughput.

### Scenario 3: Berth closure

Block one or more berths.

Observe:

- Vessel reassignment.
- Capacity reduction.
- Modeled delay.
- Unserved vessels.

### Scenario 4: Combined disruption

Increase traffic and block berths simultaneously.

### Scenario 5: Capacity expansion

Increase the number of active berths as a hypothetical experiment.

### Scenario 6: Strategy comparison

Compare supported scheduling strategies.

## Scenario outputs

- Vessels served.
- Berth assignments.
- Berth utilization.
- Modeled queue length.
- Average scheduling delay.
- Median scheduling delay.
- Maximum scheduling delay.
- Throughput.
- Unserved vessels.
- Completion time.

**Important:** The existing allocator was previously described as a deterministic greedy earliest-completion scheduler. Verify the code. Do not claim global optimization unless it is actually implemented and tested.

All What-If waiting times must be labelled modeled scheduling delays, not historical observed waiting times.
